## 1. Production was showing zero cleaners — fixed

**The symptom.** `zenex-app.vercel.app/search` displayed "0 cleaners available"
while the database held eight.

**The cause.** `utils/tokenAxios.ts` derived the tenant from the hostname by
taking the first DNS label. On Vercel the hostname is `zenex-app.vercel.app`,
so every request sent `x-Tenant: zenex-app`. The API scopes every query by
tenant and no such tenant exists, so the whole site returned empty lists — with
no error, because an empty result is a valid response. It passed locally only
because `localhost` has no dot and so sent no header at all.

**The fix.** A `resolveTenant()` helper that ignores platform hosts
(`vercel.app`, `netlify.app`, `onrender.com`, `fly.dev`, and others), apex
domains, `www`, `localhost` and raw IPs, honours a `NEXT_PUBLIC_TENANT`
override, and returns null so the API applies its own default. Genuine tenant
subdomains such as `acme.zenex.ca` still resolve. 14 test cases cover it.

**How it was missed for so long:** every check we had ran against the API
directly with curl, which never sends that header. The API returned eight
providers every time while the browser saw none.

## 2. Search and matching now use real distance

`maxRadiusKm` had been on `ProviderProfile` since the first schema and was
never read. Matching compared location strings, so a cleaner in Mississauga was
invisible to a client in Toronto 22 km away.

- New `canadian-cities.ts`: coordinate table for ~70 Canadian cities and GTA
  municipalities, plus haversine distance. No geocoding API, no network call on
  the booking path.
- Longest-name-first matching, so `Richmond Hill, ON` no longer resolves to
  Richmond, British Columbia — 3,400 km out.
- Applied in `quotes.serviceableProviders()` and `providers.findAll()`, so
  search and instant-book agree about who covers a given city.
- Unknown towns fall back to the old substring test rather than disappearing.
- The "Nearest" sort chip now actually sorts by distance; previously it silently
  fell through to rating. Providers whose town is unrecognised sink to the
  bottom instead of sorting as 0 km.

17 assertions on the distance logic.

## 4. Email: 22 templates, all wired

Moved from Resend to **ZeptoMail (Zoho)**. Templates extracted into their own
module so they can be rendered and tested without a transport.

Onboarding: welcome (client), welcome (provider), email verification, password
reset. Bookings: confirmed, new job, 24 h reminder, cancelled, rescheduled,
review request. Money: receipt with itemised GST/HST, refund, payout, Stripe
onboarding nudge, subscription started, subscription payment failed. Trust: KYC
approved, KYC rejected with reason, insurance expiring. Comms: new message,
dispute opened, dispute resolved.

Every one is now called from real code — verified by scanning each
`MailService` method for call sites, not by ticking a list. Notable decisions:

- Message emails send once per unread burst, not per message.
- Insurance warnings fire at 14/7/3/1 days rather than daily.
- Payout emails send after the transaction commits, never inside it.
- **Security fix:** templates interpolated names straight into HTML. A provider
  named `<img onerror=...>` would have had that markup delivered into a
  client's inbox. Everything is escaped now, with a test.

A browsable preview of all 22 is at `email-previews.html`.

## 6. Subscriptions: from decorative to functional

**What it was doing.** One click on the landing page created an `ACTIVE`
subscription and returned. No PaymentIntent, no Stripe subscription,
`stripeSubId` never set. Clicking "Get Premium" gave a $379/month plan for $0,
renewing forever — and delivered none of the four features on the card.

**What it does now:**

- Plan cards navigate to `/subscribe?plan=<id>`; signed-out visitors keep their
  choice through login via `returnTo`.
- The checkout page shows the total including GST/HST, the first charge date,
  the renewal cadence and the cancellation terms, with a consent checkbox that
  gates the button.
- Consent is required server-side and stored with a timestamp and the exact
  amount agreed — the evidence if a charge is ever disputed.
- Subscriptions are created `PENDING` and only become `ACTIVE` once money moves:
  immediately in demo mode, on `checkout.session.completed` in live mode.
- **Entitlements are real.** A standard clean spends an included clean and costs
  nothing; extras get the plan's discount; tax is charged on the discounted
  amount. Credit spend and booking insert share a transaction with a
  compare-and-set guard, so two concurrent bookings cannot both take the last
  credit.
- Renewals follow `invoice.paid`, using Stripe's own period end.
  `invoice.payment_failed` pauses the plan and zeroes credits;
  `customer.subscription.deleted` cancels it.
- **`cancel()` now tells Stripe.** It previously only flipped the local row, so
  a customer who cancelled would keep being charged every month while the app
  showed them as cancelled.
- Plan feature lists cut to what the code delivers. "Priority booking",
  "Dedicated cleaner" and "Same-day guarantee" removed — none exist.
- The dashboard shows cleans remaining, the discount, and a plain explanation
  when a plan is paused or awaiting payment.

All additive. A recurring stumble worth remembering: `npm run build` runs
`prisma generate`, not `prisma migrate`. A green build proves the code matches
the schema *file* — never that the database does. One commit shipped schema
changes with no migration and would have failed at runtime.
